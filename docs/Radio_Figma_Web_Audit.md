# Radio Component 1:1 Figma-to-Web Parity Audit

Built 2026-08-10. Multi-master family, same pattern as Switch (Switch/FormControlLabel/FormGroup) and Checkbox (Checkbox/FormControlLabel/FormGroup): `<Radio>`, `<FormControlLabel> | Radio`, `<RadioGroup>`, one Gallery, one Documentation frame, three MASTER COMPONENT SET sections.

## 1. Master component structure

- `<Radio>` — real `COMPONENT_SET`, node `6558:39273`, page "     Radio Group" `6558:39248`. 132 variants: `Checked` (False/True) x `Size` (Medium default/Small/**Large**) x `Color` (Primary default/Default/Secondary/Error/Warning/Info/Success) x `State` (Enabled default/Hovered/Focused/Disabled). `Disabled` is built only for `Color=Default` across all 3 sizes (6 of 132 variants) — a real, confirmed representative-color gap, same class as Checkbox's own Disabled coverage, not fabricated further.
- `<FormControlLabel> | Radio` — real `COMPONENT_SET`, node `634:100262`, 8 variants: `Label Placement` (End default/Start/Top/Bottom) x `Disabled` (False/True). **Structurally distinct from `<FormControlLabel> | Switch` and `| Checkbox`** — confirmed by node ID and by its own Radio-specific internal bindings, not a shared master. Its own token pass, not a citation of Switch's already-migrated documentation.
- `<RadioGroup>` — real `COMPONENT_SET`, node `6558:39344`, 4 variants: `Radios` (3 default/5) x `Disabled` (False/True), plus two boolean component properties (`<FormLabel>#637:0`, `<FormHelperText>#637:2`, both default `false`) toggling a real group legend and helper text. More than a spacing wrapper — confirmed via `mainComponent.parent.id` resolution that it composes real `<FormLabel>`, real `<FormControlLabel> | Radio` (which itself composes a real `<Radio>`), and real `<FormHelperText>` instances internally.
- Legacy content: the usual `_Library / Component Heading` + `Grid` wrapper (top-level frame simply named `Radio`, node `11012:147021`), containing all three real masters plus an old illustrative "Instances" grid — same "legacy content isn't named predictably" pattern as every prior component.
- Two pre-existing real-world mockups: `Radio: filter` (a loading-skeleton filter-sidebar composition, real `<RadioGroup>` instance) and `Radio: orientation` (4 real `<FormControlLabel> | Radio` instances, one per `Label Placement` value).

## 3. Completeness: real gaps, disclosed

- **Large size** (`Size=Large`, 46px, all 3 masters share this axis on `<Radio>`): a real, fully-built Figma variant with no stock MUI Radio equivalent (MUI ships `small`/`medium` only). Flagged in the Documentation frame's Sizing section with an explicit caption and footnote, and in `MuiRadio`'s own code comment — not wired into `MuiRadio`'s `styleOverrides`, same treatment as every other unmodeled-prop gap in this file (Fab's missing color variants, Drawer's missing anchor/variant axis, etc.).
- **`Disabled` state built only for `Color=Default`** (6 of 132 `<Radio>` variants): confirmed real, not silently smoothed over — the Gallery's Disabled column shows only the Default row populated, matching the set's own actual coverage.
- **RadioGroup's own `row` orientation**: no matching Figma variant exists for MUI's real `row` prop (horizontal layout); `<RadioGroup>`'s only real axis is `Radios` (3/5) x `Disabled`. Flagged in the Key Props table rather than fabricated.
- **7 `action/hover`-bound `<Skeleton>` instances** inside the `Radio: filter` real-world mockup (same disclosed, deliberately-un-migrated class Paper's and Progress's own mockups already carry — `Semantic/State/Hover` resolves to a solid tint, nothing like the translucent shimmer `action/hover` actually renders, forcing it would regress the shimmer). Belongs to `<Skeleton>`'s own future token pass.
- **4 raw-white-fill residuals on `<FormHelperText>` instances** inside `<RadioGroup>`'s own master (nodes `11443:165577`, `642:150718`, `637:93249`, `642:150726`): confirmed invisible (`visible: false`, since the `<FormHelperText>#637:2` boolean defaults off) and belong to `<FormHelperText>`'s own definition, not Radio's. Out of scope, same class of exclusion as Autocomplete's Select/MenuItem debt. 3 consecutive clean residual scans (Radio: 0, FCL: 0, RadioGroup: 4, stable across all 3 runs) confirm nothing else remains.

## 4. What was found (discovery, before and during the build)

- Zero web-side presence existed before this pass: no `<Radio>`/`<RadioGroup>` usage anywhere in `src`, no `MuiRadio`/`MuiRadioGroup` `brandTheme.ts` entry, no styleguide page, no Code Connect file. The only "Radio" hit in the whole `src` tree was a prose mention in `switcher/page.tsx`'s Usage Guidelines copy, not real code. Genuinely a blank slate, unlike every prior component in this file.
- The raw white component-root fills on both `<FormControlLabel> | Radio` (8 variants) and `<RadioGroup>` (4 variants) were confirmed **actually rendered**, not inert — verified by tracing the fill to each variant's own root `COMPONENT` node (`clipsContent: false`, `visible: true`) and by direct `fills` array inspection (not by screenshot alone, since the screenshot tool flattens transparency against a white matte and would have shown white either way — a real instance of "trust node data over a suspicious render" from this project's own gotcha list). Real MUI `<FormControlLabel>` and `<RadioGroup>` render with zero background, so this was a structural bug, not a design intent — most likely the same `figma.createAutoLayout()` default-white-fill-never-cleared pattern documented in `figma-component-structure.md` §1.4, just on a component root instead of doc chrome.
- Checked `mainComponent.parent.id` resolution across `<RadioGroup>`'s own internal composition and both real-world mockups (`Radio: filter`, `Radio: orientation`) before any structural changes — all instances resolved cleanly to the three real masters, zero orphans, both before and after the extraction/reparent into the new Gallery.
- Cross-component composition check (Dialog, Drawer — the two candidates named in Step 1): zero Radio-family instances found in either. Not a file-wide scan across all ~74 pages, flagged as a scope limit rather than presented as exhaustive.

## 5. What was built

- **Token rebind:** 216 mutations across `<Radio>`'s 132 variants (132 dot/ring fills + 84 halo fills), 16 mutations across `<FormControlLabel> | Radio`'s 8 variants (8 dot fills + 8 label-text fills, plus 8 white-fill clears), 12 mutations across `<RadioGroup>`'s 4 variants (4 FormLabel-text + 4 HelperText fills, plus 4 white-fill clears). 3 consecutive clean residual scans, disclosed 4-node RadioGroup residual stable across all three (see §3).
- **Legacy cleanup:** duplicated the legacy `Radio` wrapper as a safety net before touching anything, reparented all three real masters directly out of the original (preserving their node IDs, confirmed zero broken instance links via a pre/post `mainComponent` resolution check — 74 Radio-family instances page-wide, 0 unresolved), archived the now-emptied original to `🗄️ _Archive / Deprecated Docs` as `_Archive / Radio / 2026-08-10 / Radio (...)`, locked, then deleted the now-unneeded safety duplicate.
- **`Radio - Component Gallery`:** cloned Checkbox's Gallery chrome (Top Header + Gallery Header, closest precedent — same "control + own-FormControlLabel + own-group-wrapper" trio shape as Switch's family) and retexted for Radio. Three `MASTER COMPONENT SET` sections, each the real, live `COMPONENT_SET` reparented directly (never rebuilt from `createInstance()` copies):
  - `<Radio>` section: axis labels computed from the set's own real child x/y clusters, not assumed from a sibling — confirmed the grid is **State-major/Size-minor on X, Color-major/Checked-minor on Y**, the inverse of Checkbox's own Color-major-X/State-major-Y layout (same "always derive from real geometry, never assume a sibling's axis convention" lesson FAB's pass already hit). 37 label texts (4 State majors, 12 Size subs, 7 Color majors, 14 Checked subs), styled/toned identically to Checkbox's own axis-label convention (cloned label nodes for exact style fidelity rather than hand-rebuilding text styles).
  - `<FormControlLabel> | Radio` section: reused Checkbox's exact axis-label positions verbatim, since Radio's FCL variant geometry is pixel-identical to Checkbox's own (`End`/`Start`/`Top`/`Bottom` x `Enabled`/`Disabled`).
  - `<RadioGroup>` section: **caught and fixed a real axis-orientation mistake mid-build** — initially assumed Checkbox's FormGroup template's row/column assignment (Radios-count on columns, Enabled/Disabled on rows) without re-verifying against RadioGroup's own real child coordinates; a direct geometry check showed the opposite (`Disabled` is the real X/column axis, `Radios` count is the real Y/row axis) — fixed before calling the section done, not left silently wrong.
  - Two `REAL-WORLD USE CASE` sections reparenting `Radio: filter` and `Radio: orientation` unmodified, per instruction — the filter mockup's real 1440px width sits comfortably inside the Gallery's 2393px content column, no width-cascade fix needed this time (unlike Chip's/Dialog's own precedent, since Radio's mockup happens to fit).
  - 3 consecutive verification checks: 0 unresolved instances, 74 Radio-family instances page-wide, exactly 2 top-level frames on the page (Two Core Frames Architecture satisfied).
- **`Radio - Documentation`:** cloned Checkbox's Documentation frame wholesale (Intro Block → Visual Preview → Sizing → Anatomy & Token Architecture → Usage Guidelines & Accessibility → Key Props, the ratified shape, no separate Interactive States/Specs sections) and edited every section in place with real content:
  - Visual Preview rebuilt with real instances: 4 status-color swatches (Base States), Default across all 4 interactive states (Interactive States), 4 real `<FormControlLabel> | Radio` label placements (Label Placements) — no fabricated content, every instance is `createInstance()` off a real, confirmed variant.

  - Anatomy & Token Architecture rewritten in full: 5 anatomy paragraphs (dot/ring glyph, halo mechanism with the Checkbox-Ripple-reuse callout, FormControlLabel composition, RadioGroup composition, sizing) and 6 Token Architecture bullets (2 more than Checkbox's 4, added as new bullet-list children rather than cramming extra findings into existing ones) covering every row of the §2 mapping table, including the flagged Brand-tier neutral-primitive gap and the white-fill structural fix.
  - Usage Guidelines & Accessibility rewritten with Radio/RadioGroup-specific guidance (mutual exclusivity via shared `name`, `role="radiogroup"`, native `input type="radio"` keyboard semantics).
  - Key Props table rewritten: 6 real `<Radio>` props (`checked`, `color`, `disabled`, `size` with the Large flag inline, `value`, `name`) + 3 real `<RadioGroup>` props (`onChange`, `value`, `row` — flagged as having no matching Figma orientation variant), replacing Checkbox's 9-row set of checked/indeterminate/etc.

## 6. Web side

- **`MuiFormControlLabel`:** already exists (`root: { gap: baseTheme.spacing(1) }`), generic layout fix with no color/typography override — confirmed it already benefits Radio automatically, no extension needed.
- **`MuiRadioGroup`:** verified directly against `node_modules/@mui/material/RadioGroup/RadioGroup.js` that `<RadioGroup>` renders `<FormGroup role="radiogroup" ...>` directly with no distinct styled wrapper — the existing `MuiFormGroup` `gap: 8` override already applies automatically. No new entry needed; a comment documents why rather than adding a no-op key. The Figma-side `Components/Radio/Label/*` tokens (RadioGroup's own composed `<FormLabel>`/`<FormHelperText>`) have no code home yet since neither has a `brandTheme.ts` entry — out of scope, flagged below.
- **`MuiRadio`:** new entry, and smaller than expected after verifying `node_modules/@mui/material/Radio/Radio.js` directly (same discipline as FAB's own "zero color overrides needed" finding):
  - **Zero code needed** for all 6 named checked-dot colors — stock Radio.js already applies `theme.palette[color].main` via its own internal generic loop, already confirmed byte-identical to the approved Semantic/Status tier targets.
  - **Zero code needed** for the Default/unchecked ring color either — stock Radio.js's base icon color reads `theme.palette.text.secondary` directly, which this theme already defines as the literal `'rgba(0, 0, 0, 0.6)'`, an exact match to the new `Components/Radio/Icon/Default` token.
  - Geometry (42px Medium / 38px Small, 9px padding) written explicitly for defensiveness, though it was confirmed to already equal MUI's own stock defaults.
  - Hover/Focus deliberately kept as the same flat, global `action.hover`/`action.focus` `MuiCheckbox` already uses, rather than reconstructing all 14 approved `Components/Checkbox/Ripple/*` values as genuine per-status code — that richness is real and already reused directly on the Figma side, but Checkbox's own shipped code already simplifies the same tier to one flat overlay in code, and matching that existing precedent was judged lower-risk than guessing at exact per-color opacity math outside what this theme's `colors` module predictably exposes. Flagged here, not silently mismatched.
- **Zero existing usage anywhere in `src`** (confirmed by grep, see §4) — there is nothing to regression-check on the web side, stated explicitly per instruction rather than skipped.
- `npx tsc --noEmit` clean after the `brandTheme.ts` edit.
- No styleguide page built, per the ongoing Storybook-pause process change (applies from Drawer onward).
