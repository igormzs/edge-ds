# EDGE-DS Migration Status

Tracks the MUI-palette → EDGE-palette Figma token migration, component by component. This is the repo-visible counterpart to Claude's private cross-session memory notes — update both together whenever a component's status changes. This file is intentionally a summary (current state + key decisions); the detailed blow-by-blow history, gotchas, and full audit trail live in Claude's memory and in this directory's per-component `*_Figma_Web_Audit.md` files where they exist.

Canonical SOP: [`figma-component-structure.md`](./figma-component-structure.md) (component migration workflow, token-tier rules, Two-Frame Architecture) and [`web-component-page-pattern.md`](./web-component-page-pattern.md) (paired web styleguide pattern).

**Figma file:** `EDGE Design System - New`, fileKey `fLQNXhHQhKBZzWnJGtUcwn`.

**Standing rule:** Figma is the source of truth for tokens/colors — code (`brandTheme.ts`, Storybook) must always be brought to match Figma's live values, never the reverse.

**Standing gotcha:** never trust an old "✅ / Locked" mark on a page as proof of full migration completeness without re-verifying live — this has been wrong more than once on this project.

### Stepper — tranche detail

Structurally the most complex family tackled so far: 5 real component structures (`Step Icon`, `<Step>`, `<MobileStepper>`, `<DesktopStepper>`, `<Stepper>`), split into 4 gated tranches rather than one combined pass, given real architecture issues found (not just token gaps).

  - Both fully retokenized off `MUI palette`. Two new shared tokens created: `Semantic/Status/Error/Default` (alias → `Brand/Error/700`) and `Semantic/Status/Info/Default` (alias → `Brand/Info/700`) — named `/Default` since neither existing `/Main` (500-tier) nor `/Icon` (800-tier) role matched the required `/700` value. Warning recolored to `Brand/Warning/800` for cross-component consistency with Alert/Chip/Badge (a deliberate value change, not a byte-match to the old raw value). `Semantic/Status/Success/Icon` reused as-is (exact match).

  - Active-state icon confirmed to need no new variant — it's the same `State=Default` master as Inactive, differentiated only by a per-instance fill-color override (confirmed via Figma's own `overrides` API, no other property differs).

**Real Figma automation gotchas hit and fixed during this build, worth remembering for any future single-component-to-variant-set promotion:**
- **`combineAsVariants` inherited a shared TEXT component property from the original single component, silently discarding each new variant's distinct authored text.** The original component already exposed `Title`/`Hint` as TEXT properties; every clone inherited the same property references, so `createInstance()` on any variant rendered the *property's default value* ("Click to upload...") instead of that variant's own real content (e.g. Error's "Upload failed"), even though the master's own canvas appearance was correct. ## Known systemic gaps (not component-specific)

- **No spacing/sizing token bindings anywhere in the file.** A real `Sizing/1`–`12` (8px scale) collection exists but is never bound to any padding/gap property in any component or documentation frame checked so far. Deliberately deferred to its own future project, not picked up opportunistically.
- **`Brand/*` primitive tier has no neutral/grey/black family** beyond `White` — components needing a non-brand-colored icon/text have had to alias to `Neutral/*` (a separate tier that was closed 2026-08-12) or, in rare cases, hardcode with an explicit flagged exception.
- **Documentation-chrome zero-hardcode rule**: any Gallery/Documentation frame chrome (labels, captions, wrapper backgrounds) authored during a migration must bind to real tokens, never literal hex — violations get audited and fixed (see Colors foundations' zero-hardcode pass) rather than left silently in place.
- **A clean color-token audit does not imply a clean text-style audit — they're independent checks.** Confirmed on Toggle Button: every text node passed as far as fill-color tokens go, but every single one had an empty `textStyleId`, manually set to `Inter` (not the real Montserrat/Open Sans/Roboto system) — invisible to a paint/fill scan since `textStyleId` and fill color are separate bindings (§3 of `figma-component-structure.md`). Worth a dedicated `textStyleId` spot-check on any earlier "✅ Migrated" component above that was closed via a color-token audit alone, since none of those closures explicitly mention checking this.
- **Key Props table's Prop Name + Type columns are unbound on at least one long-ratified page.** Button's row 1 (the table's original template row) has an empty `textStyleId` on its first two cells while every other row is bound — confirmed 2026-09-16 while tracing why Card's and Tag's own Key Props tables had the same gap on *every* row (both had evidently cloned that one broken row repeatedly). Card's and Tag's instances were fixed; Button's single-row instance was left as-is, out of scope for that pass. Worth a spot-check on any other page whose Key Props table was built by cloning an existing table rather than the clean shared template.
- **`_Pattern / Users Management Table` (used across all 5 breakpoints of Screens' "User management" section) has 150 text nodes with no bound `textStyleId`**, using hand-set dense-table font sizes (7px column headers/body, 6.5px chip labels) smaller than any existing EDGE type-ramp step (`input/label` at 12px is the smallest). Confirmed not a scaling artifact — real, crisply-rendering content, just never bound to a named style, likely because no style small enough exists yet. Flagged 2026-09-21 during Screens' typography audit; needs a deliberate pass (new compact type-ramp step, or a design call to resize the table) rather than a forced bind that would visibly change the table's density.
- **`<Select>` (`6570:41424`, 72 variants) has an unbound white background fill on essentially every variant** — 144 instances found (root + nested `<FormHelperText>`) during Headings' 2026-09-21 token audit, surfaced via a "Sort" dropdown instance. Flagged, not fixed — real scale work, deserves its own deliberate pass with spot-checks, not an opportunistic fix. If `<Autocomplete>`/`<TextField>` share the same underlying dropdown-shell pattern, worth checking whether they have the identical gap before assuming it's Select-only.
