## 3. Completeness: two flagged reconciliation gaps, plus one architecture question

**Gap 1, `CleanInputs` has no web counterpart.** Exists as a real Figma master with no matching SVG anywhere in `public/icons/edge/`. Not built or exported, flagged for design to decide on cleanup or export.

**Gap 2, three web SVGs have no Figma counterpart.** `check.svg`, `heart.svg`, `star.svg` are generic, lowercase-named files with no matching Figma master under any name, likely legacy or test assets predating the current icon set. Flagged for design to decide on cleanup, not investigated further.

**Not pursued, by explicit instruction:** the 5 `_hidden` Figma masters and the 5 `_hidden-1` through `_hidden-4`/`_hidden` web files match by count but not by name (all 5 Figma masters share the identical literal name `_hidden`, no distinguishing suffix). A visual/hash pairing exercise to match them 1:1 was explicitly not pursued, not worth the effort for non-production placeholders.

**Architecture question, flagged not resolved:** whether icons should own a fixed fill color at all, versus inheriting `currentColor` from context (the more typical icon-system pattern, and arguably more correct for a design system than a single hardcoded semi-transparent black baked into every master). This pass only migrated the *token* an existing fixed-fill approach points to; it did not revisit whether a fixed fill is the right approach at all. Explicitly a design/architecture decision for a future pass, not engineering leftovers.

## 4. What was found (discovery, before any build)

- A hybrid structure: one real generic sizing/instance-swap wrapper plus 125 independent single-icon masters, not a single enumerable grid like Button's or FAB's own `COMPONENT_SET`.
- All 125 masters' fills were assumed uniform in the initial 25-icon sample (Step 2), but a full pass across all 125 found 16 icons (9 zero-`action/active` file-type/trend icons plus 7 two-tone icons) with real, intentional, non-uniform coloring, caught only by checking every icon's actual fill bindings before rebinding, not trusting the earlier partial sample.
- The legacy `_Library / Component Heading` + `Grid` wrapper pattern was present, same as every other pre-2026-08 component page, needing the same archive-and-rebuild treatment.
- `Semantic/Icon/Default` already existed in the EDGE palette collection with a real, exact value match (verified by resolved RGBA, not name), and already had two points of real precedent elsewhere in the file (Checkbox's own alias, Autocomplete's prior dropdown-icon migration).

## 7. 2026-08-07 chrome token rebind: Gallery/Documentation raw-hex cleanup

**Root cause.** A 2026-08-03 audit found and fixed raw/literal chrome colors (card backgrounds, borders, captions, body text) baked into the `Component Doc - EDGE-DS` master template, mapping them to existing `Semantic/*` and `Documentation/*` tokens. That fix does not retroactively reach frames cloned from an already-drifted ancestor. Icons' frames were built 2026-08-06 from such a drifted lineage, so the same gap recurred here, not a new defect.

**What was rebound.** 171 raw fills/strokes across `Icons - Component Gallery` and `Icons - Documentation` chrome: a systemic raw grey (`#9E9E9E`) caption color reused identically across all 130 icon/preview swatch captions → `Semantic/Text/Tertiary`; white card/frame backgrounds → `Semantic/Surface/Paper` and `Documentation/Surface/Page`; black body/bullet text → `Semantic/Text/Primary`. The `<Icon>` wrapper's own 4 `Size` variants and a spot-check of ~20 icon masters' root-level fills/strokes were reconfirmed clean, exactly as before — this pass touched chrome only, never the already-migrated 125-icon vector-fill inventory.

**Correction to the prior discovery pass.** The earlier audit flagged 20 icon masters (+1 preview instance) as carrying an "invisible raw-white fill." Direct inspection before touching anything found this was inaccurate: every one of those paints is already bound to `Semantic/Surface/Paper`, just `visible:false`. There was no raw-hex gap there at all, so nothing was stripped or rebound — leaving them exactly as found.

**Content investigation, not a defect.** A parallel discovery pass had flagged that the Anatomy & Token Architecture section's `Component Placeholder Slot` appeared to contain stale Checkbox-topic prose. Checked live `.characters` directly (not the node's `.name`, which Figma never re-syncs after a text edit): the real content is fully correct, Icons-specific prose (confirmed identical to what's already documented in §5 above). No duplicate content exists; this was a stale-name false read, not a content bug.

**Verification.** 3 consecutive clean residual scans, 0 remaining matches for any of the raw chrome values. Visual spot-check confirmed no rendering regression.
